# SlabReinforcement User Messages Design

**Date:** 2026-04-21

## Goal

Сделать пользовательские сообщения в SlabReinforcement инженерными, короткими и прикладными.
Пользователь должен видеть только то, что помогает:

- выбрать нужные цвета;
- назначить тип арматуры и шаг;
- понять, будут ли созданы зоны;
- исправить только те настройки, которые мешают построению.

Внутренние алгоритмические термины и техническая диагностика не должны попадать в основной пользовательский интерфейс.

## Current Problems

Сейчас в пользовательский интерфейс и итоговые сообщения попадают внутренние термины системы:

- `кластеры`;
- `тривиальные кластеры`;
- `уровни Z` со списком отметок;
- `face`;
- `горизонтальных face`;
- `пропущено face`;
- `группы`;
- сырые `ex.Message`.

Из-за этого окно выглядит как диагностический экран для разработчика, а не как рабочий инструмент инженера.

Дополнительно часть видимых строк в `SlabReinforcementWPF.xaml` остаётся в битой кодировке, что ухудшает читаемость интерфейса.

## Product Decision

Принимаем режим **engineer-first UI**:

- инженеру показываются только понятные и полезные сообщения;
- внутренние технические признаки используются только для принятия решения о тексте;
- если сообщение не помогает принять действие, оно удаляется;
- если проблема не блокирует работу и не требует решения со стороны инженера, она не показывается;
- итоговые сообщения должны говорить о результате и о нужных действиях, а не о внутреннем состоянии алгоритма.

## User-Facing Language Rules

- Использовать термины предметной области: `зоны`, `участки`, `тип арматуры`, `шаг`, `отметки`, `импортированный файл`.
- Не использовать внутренние термины: `кластер`, `группа`, `face`, `trivial`.
- Не выводить списки координат и длинные перечисления служебных значений.
- Не показывать сырые сообщения исключений, если их можно заменить понятной формулировкой.
- Каждое предупреждение должно отвечать на вопрос: `что не так` и, по возможности, `что проверить`.

## UI Changes

### Main Window

В окне `SlabReinforcementWPF.xaml`:

- исправить битую кириллицу во всех видимых строках;
- сократить status summary до краткого состояния, например: `Выбрано 9 цветов, ожидается 177 зон`;
- убрать технические колонки:
  - `Face`;
  - `Гориз.`;
  - `Пропуск`;
  - `Уровни Z`;
  - `Угол`;
- заменить колонку `Предупреждения` на колонку `Примечание`;
- оставить в таблице только данные, нужные для настройки:
  - выбор цвета;
  - цвет;
  - ожидаемое количество зон;
  - тип арматуры;
  - шаг;
  - краткое примечание при наличии действия;
- правый блок предупреждений оставить, но показывать там только короткие инженерные замечания без внутренних терминов;
- если замечаний нет, не показывать псевдопредупреждение вида `ручной прогон перед релизом обязателен`.

### Preview / Summary

В summary preview:

- оставить направление;
- оставить количество выбранных цветов;
- оставить прогноз количества зон;
- убрать технические величины, которые не помогают принять решение;
- не показывать `группы`, `кластеры`, `тривиальные кластеры`, служебные счётчики и внутренние диагностические метрики.

## Message Mapping

Технические признаки должны преобразовываться в инженерные сообщения по таким правилам:

- `MissingRebarTypeFaceCount > 0` -> `Есть участки без типа арматуры.`
- `InvalidSpacingFaceCount > 0` -> `Есть участки с некорректным шагом армирования.`
- `EstimatedZoneCount == 0` при выбранных цветах -> `По текущим настройкам зоны не выделяются. Проверьте допуски или направление.`
- несколько отметок -> `В импортированном файле есть участки на разных отметках. Проверьте, что выбран нужный фрагмент.`
- пропущенные негоризонтальные грани -> `Часть участков не учтена при построении зон.`

Следующие признаки не должны показываться пользователю напрямую:

- количество кластеров;
- количество тривиальных кластеров;
- численные списки отметок;
- внутренние углы;
- внутренние группировки.

Если признак не ведёт к понятному действию, он должен быть удалён из пользовательского текста.

## Command Dialog Changes

В `SlabReinforcementCommand.cs`:

- оставить только блокирующие ошибки и итог результата;
- не показывать пользователю сырые `Exception.Message`, кроме случаев, когда без них невозможно объяснить проблему с файлом;
- итоговое сообщение после построения должно быть коротким:
  - `Создано зон: N.`
  - `Есть участки без типа арматуры.`
  - `Есть участки с некорректным шагом.`
- сообщения вида `тривиальные кластеры`, `короткие пути`, внутренние детали создания не показывать в обычном режиме.

## Architecture

Добавляется отдельный слой преобразования диагностики в пользовательские сообщения.

Предлагаемая ответственность:

- `ZoneGeometryEngine` и `ZonePreviewAnalyzer` продолжают считать факты и признаки;
- новый formatter/helper получает summary/analysis и строит короткие инженерные тексты;
- `SlabReinforcementWPF` показывает только formatter output;
- `SlabReinforcementCommand` использует тот же подход для TaskDialog.

Такой подход позволяет сохранить техническую логику внутри системы, но перестать проталкивать её напрямую в UI.

## Error Handling

- Блокирующие ошибки остаются явными.
- Неблокирующие проблемы показываются только если инженер реально может на них повлиять.
- Неинформативные технические сообщения удаляются.
- Одна проблема должна формировать одно понятное замечание без дублей.

## Testing

Перед реализацией добавить падающие smoke/regression tests на formatter layer:

- технические термины не попадают в итоговые пользовательские сообщения;
- сообщения про `тип арматуры` и `шаг` остаются;
- при нулевом результате выдаётся только инженерная рекомендация;
- при отсутствии проблем warning list остаётся пустым;
- битая кириллица не остаётся в видимых строках окна.

Проверка после реализации:

- `dotnet build SlabReinforcement.sln -c R2026`
- `dotnet run --project SlabReinforcement.StartupSmoke/SlabReinforcement.StartupSmoke.csproj -c R2026`

## Scope Guard

В эту задачу не входит:

- полная переработка алгоритма построения зон;
- изменение геометрического ядра без необходимости;
- добавление отдельного режима `Подробнее`;
- внедрение новой системы логирования.

Задача ограничена очисткой пользовательского языка, сокращением шума и сохранением только полезных инженерных сообщений.
