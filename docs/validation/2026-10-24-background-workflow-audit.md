# Проверка процесса фонового армирования

Запрос: разобраться, понятен ли текущий процесс и хорошо ли работает основной фон. Проверка 24.10.2026; production-код и установленная сборка не изменялись. Изменён только отдельный испытательный стенд для воспроизведения поведения окна.

**Последующее уточнение пользователя:** требуется native AreaReinforcement, отдельно для каждого слоя, с готовыми шаблонными типами `*-пог.м.`; нахлёст учитывается отдельно. Поэтому отсутствие нарезки длинного элемента не является само по себе дефектом выбранного сценария учёта погонажом. Ниже сохранены результаты аудита прежнего Rebar-планировщика, а не требования автоматически переносить все его правила в новый вариант. См. docs/superpowers/specs/2026-10-24-native-area-background.md.

## Текущий путь пользователя

1. Выбрать плиту и прямое ребро — локальное направление X; Y перпендикулярно ему в плоскости плиты.
2. На вкладке «Фон и обрамление» включить нужные из четырёх слоёв, выбрать тип и максимальный шаг каждого. Подложка не требуется.
3. При необходимости включить П-обрамление и задать контуры, тип, максимальный шаг, вылет лапки.
4. Дождаться общего предпросмотра и нажать «Создать армирование». Операция учитывает включённые компоненты обеих вкладок, независимо от текущей вкладки.
5. При повторном запуске полностью совпавший фон используется как существующий. Изменение параметров не является командой редактирования ранее созданного армирования.

## Что подтверждено

- Свежий запуск существующих BackgroundPlannerTests, MaximumSpacingLayoutTests и ActualFootprintPerimeterTests: 15/15 PASS. Крайние ряды, отверстия, максимальный шаг, реальные дуги и согласование геометрии фона с П проверяются алгоритмами.
- Прежний фактический Revit-прогон run-20261024-142330 создал фон без CAD: 820 стержней / 28 наборов (22 MaximumSpacing, 6 одиночных), максимальный шаг 200 мм. Физические оси сверены с планом и сохранённой/открытой моделью. Это историческая проверка соответствующей сборки, а не новый полный прогон создания.
- Новый Revit 2023 build23.0.11.19, run-20261024-152353, проверил реальное WPF/BAML и TryCaptureParameters текущей DLL 2450739AE616F709BDC9E5F936532E2E8D05D546C77BF58E3E17293BF3320476. Восемь проверок стенда PASS, включая воспроизведение дефекта ниже. Модель и настройки не изменены, транзакций записи нет. PASS здесь означает успешное воспроизведение заданного поведения, а не отсутствие дефектов.

## Найденные проблемы и ограничения

| Приоритет | Наблюдение | Основание / что требуется |
|---|---|---|
| Исправить | Выключенные зоны могут блокировать фон. | WPF.xaml.cs:378–383 безусловно проверяет объединение/смещение зон и округление. В реальном Revit при IncludeZones=false и одном включённом слое `bad` в каждом из трёх полей переводит валидный ввод в ошибочный. Валидацию разделить по участвующим компонентам. |
| Исправить | Повторный запуск с другим диаметром может добавить второй фон при разрешённых пересечениях. | ReinforcementSession.cs:159 заранее отфильтровывает другой физический диаметр, поэтому проверка несовпадения его не видит. Core-проба 4000×3000, Ø12→Ø16: 74 старых + 74 новых, запрета геометрического валидатора нет. Ветка Session проверена по коду; запись этого случая в Revit не испытывалась. Нужен явный отказ или отдельная согласованная операция изменения фона. |
| Исправить | Узкий отдельный остров может исчезнуть из раскладки без специальной диагностики. | Core-проба: острова 4000×3000 и 4000×60, защитный слой25, Ø12. После отступа31 малый остров исчезает; CanCreate=true, 16 стержней большого острова. BackgroundPlanner.cs:59,91 проверяет наличие стержней по слою в целом. Требуется диагностика непокрытой части исходной плиты. |
| Определить сценарий | Длинные стержни не делятся на поставляемые части и стыки. | На точном контуре тестовой плиты текущая Core DLL даёт 820 стержней, максимальная длина41637,898мм; 758 длиннее12000мм. 12000 здесь только порог подсчёта, не назначенная проектная/нормативная длина. Настройка «Стандартная нарезка» относится к зонам и на фон не действует. Пользователю задан вопрос о необходимом сценарии. |
| Сделать явным | Боковой отступ переносится между плитами. | WPF.xaml.cs:91 предпочитает сохранённое значение новому SideCoverMm. Если сохранено50, следующая плита с боковым слоем25 использует50. Верх/низ берутся из плиты; отступ меньше требуемого блокируется. Нужны явные «из плиты / задан вручную» и видимые текущие значения. |
| Сделать явным | Порядок слоёв и влияние обрамления не видны в плоском предпросмотре. | BackgroundPlanner.cs:139: X ближе к соответствующей поверхности, Y внутри X. При П добавляются отступы внутрь. Нет выбора порядка и отображения положения по толщине. Нужна компактная схема сечения/фактические отметки. |
| Сделать явным | Состав операции зависит от обеих вкладок. | Зоны включаются после выбора CAD и остаются включены при возвращении на вкладку фона. Общий счётчик не показывает состав. Перед созданием нужен краткий список включённых компонентов. |
| Сделать понятным | Полностью существующая раскладка показана как ошибка создания. | Реальный UI с подставленным reference-only планом отображает «Создание недоступно», при том что новых стержней просто нет. Это проверка представления состояния, не новая проверка чтения существующей модели. Нужен нейтральный статус «Уже существует». |

## Следующий порядок работы

Сначала исправить независимость ввода фона и защиту повторной операции; затем сделать видимыми защитные слои, порядок X/Y и состав создания. По ответу пользователя определить сценарий ограничения длины и стыков основного армирования. После этих изменений выполнить отдельную приёмку блока 1 в Revit, включая реальные повторные запуски с изменённым диаметром/шагом.

Доказательства: `artifacts/background-workflow-audit/bar-lengths.json`, `artifacts/underlay-ui-smoke/run-20261024-152353/results.json`, прежний `artifacts/single-slab-revit/run-20261024-142330/results.json`. Инженерная достаточность узлов в этой проверке не оценивалась.
